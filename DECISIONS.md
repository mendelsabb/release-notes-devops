# Decisions

**Assumptions.** Local cluster is kind; dev and prod are namespaces in one cluster. Each environment
gets its own in-cluster Postgres ("together with its datastore"). It's an internal tool, so the UI has
no authentication. For "update what gets deployed" I chose GitOps.

**Trade-offs**
- **FastAPI + Postgres + Alembic.** Boring and typed. Uniqueness is a DB constraint (concurrent
  duplicates → one `201`, the rest `409`). Migrations run once per deploy in an Argo CD sync-hook Job
  before the new pods, and must be expand/contract because old pods keep serving during a rollout.
- **One Helm chart; environments are folders, not branches.** `gitops/environments/<env>/` holds
  `values.yaml` (config) and `image.yaml` (digest). A root app syncs an ApplicationSet that creates
  one Argo CD app per folder.
- **GitOps, build once / deploy many.** CI never touches a cluster: it publishes to GHCR and commits
  the digest for dev; prod moves only by a PR that copies that digest (or restores the previous one
  on rollback). Code and config share one repo because the brief asks for one; at work I'd split them.
- **Zero downtime, measured.** `maxSurge 1 / maxUnavailable 0`, DB-aware readiness, 5 s preStop,
  20 s drain, 35 s grace. An in-cluster client saw 0 failed of 6,004 requests across a rollout and
  0 of 24,001 through a failed release and its rollback.
- **Postgres is persistent, not HA:** a restart costs 2–3 s of `503`s. Secrets are generated by
  `make up`, never committed.

**Beyond the brief, on purpose:** Loki/Alloy (logs), the offline local mode (so a reviewer without
push rights can run the full loop) and the CI-built fault image for the failed-rollout drill. The core
works without any of them, and they're the first things I'd cut.

**Cut for time:** HA database and backups, External Secrets, TLS/Ingress, alerting/SLOs, canary
analysis, image signing.

**What would still break zero-downtime in a real cluster**
- Crashes skip the drain (SIGKILL: 4–8 refused connections) → client/proxy retries, more replicas.
- Keep-alive connections closed by a draining pod (11 of 6,003 without retries) → retrying clients or an L7 proxy.
- Load balancers and Ingress propagate slower than kube-proxy → longer preStop.
- Non-backward-compatible migrations, DB failover, no room for the surge pod.

**Many clusters:** a separate config repo; an ApplicationSet cluster generator; promotion in waves
(canary cluster → region → global) gated by SLO analysis (Argo Rollouts/Kargo); clusters, managed
Postgres and Argo CD bootstrapped by Terraform; secrets via External Secrets; signed images.

**AI assistance.** I built this with an AI assistant (Claude) under my direction, and verified every part
by running it on a kind cluster and on GitHub (`docs/verification.md`). That surfaced real bugs:
an HPA sync-wave deadlock, a vendored-OpenSSL CVE, and a CI publish race.
