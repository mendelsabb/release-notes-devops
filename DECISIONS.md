# Decisions

## Trade-offs

- **FastAPI + SQLAlchemy + Alembic + PostgreSQL.** Boring, well understood, typed. Uniqueness is a
  Postgres constraint, not an app-side check, so concurrent duplicate posts give exactly one `201`
  and the rest `409`. Migrations run once per deploy in an Argo CD sync-hook Job, ordered after the
  DB and before the Deployment, and never at pod startup. Migrations must be expand/contract
  (backward compatible), because old pods keep serving while new ones start.
- **kind + one Helm chart, two values files.** dev and prod differ only in
  `gitops/environments/<env>/values.yaml`. The image is a separate `image.yaml` per environment and
  is the only file automation ever edits, so a rollback cannot revert config by accident.
- **GitOps with Argo CD, build once / deploy many.** CI never touches a cluster. It publishes an
  image and commits its **digest**. Promotion copies that exact digest to prod in a reviewed commit,
  and rollback restores the previous digest from git history. Locally, Argo CD watches an
  in-cluster git server that mirrors your checkout, so a reviewer can run the whole loop without
  push rights to my GitHub or a GHCR account. With a hosted repo only `repoURL` changes.
- **Zero-downtime settings, measured rather than assumed.** `maxSurge 1 / maxUnavailable 0`,
  readiness checks the DB, `minReadySeconds 5`, a 5 s `preStop` sleep (endpoint removal is
  asynchronous), uvicorn drains for up to 20 s, and the grace period is 35 s. An in-cluster load
  generator recorded **0 failed of 6,002 requests** across a v1.0.0 → v1.1.0 rollout, and 0 failures
  across rollback, a failed rollout and pod deletion.
- **Observability:** Prometheus (annotation discovery, no operator), Grafana with a provisioned
  dashboard, and Loki + Alloy with JSON logs and `level` as the only extra label. All charts are
  sized for a laptop (about 4 GB in total).
- **Postgres is a single StatefulSet replica with a PVC: persistent, not highly available.**
  Restarting it measured about 2–3 s of `503`s (48–80 of ~3,600 requests). Readiness stops routing traffic
  but cannot create a database. The DB secret is generated by `make up`, not stored in git.

**Cut for time:** an HA database (operator or managed), External Secrets/Sealed Secrets, TLS and
Ingress, alerting rules/SLOs, progressive delivery (canary/analysis), image signing and admission
policy, and backups.

## What would still break zero-downtime in a real cluster

- **Crashes, not deploys.** A SIGKILL'd pod caused 4–8 connection-refused errors in our tests. Fix:
  client or proxy retries for idempotent requests, outlier detection, more replicas.
- **Long-lived keep-alive connections** stay pinned to a draining pod; when it closes them, a request
  racing the close fails (measured: 11 of 6,003 with a non-retrying client). Fix: clients/proxies
  retry idempotent requests on a reset reused connection (browsers do), or an L7 proxy/mesh.
- **External load balancers and Ingress** have their own propagation delay. The `preStop` sleep
  must cover the slowest path (cloud LB health checks are often 10–30 s).
- **Non-backward-compatible migrations** (rename or drop column) break old pods mid-rollout. Use
  expand → deploy → contract across releases.
- **Database maintenance or failover** is downtime for this design. Fix: managed HA Postgres plus
  connection retry.
- **Node drains and autoscaling**: covered by the PDB (`minAvailable 1`), but only if there is
  enough capacity to schedule the surge pod. Pending pods stall rollouts (`progressDeadlineSeconds`
  turns that into a visible failure).

## Many clusters, for real

One Git repo with an overlay per cluster (or an ApplicationSet with a cluster generator). Promotion
by wave (canary cluster → region → global), gated by SLO-based analysis (Argo Rollouts/Kargo), not
by a person reading dashboards. The registry and digests stay the same everywhere (build once).
Secrets come from a secret manager via External Secrets. Postgres would be managed HA, not in-cluster.

## AI assistance

I built this with an AI coding assistant (Claude), which drafted code, manifests, scripts and docs
under my direction. Every component was executed and verified on a real kind cluster (see
`docs/verification.md`), and I can explain each line. Several defects were found by running the
system rather than by review. Examples: a sync-wave deadlock caused by the HPA, Argo CD retries
pinning a stale revision, a vendored-OpenSSL CVE in `psycopg[binary]`, and bash 3.2 incompatibilities.
